# Frozen SSA v2 runtime gap: actual text/sort images

This is a static machine-code/source audit, not a runtime experiment. No benchmark executable was run and no clock data was collected. No tracked file changed. `manifest.json` preserves commands and SHA256. All six images exactly match `build/ssa-pruned/user-profile/metadata.json`: off text38860ccc/sort3a981e30, on textee3a0e56/sort6d818ce2, C text5bb255bd/sortfc05785a. The off images are retained images; on/C are byte-identical reconstructions because performance.py deletes its temporary images. Stale build/runtime-bench binaries were explicitly excluded. Clang is the recorded -std=c11 -O3 -ftrapv compiler; sources/flags were unchanged.

## What remains in the actual instructions

The counts below describe **selected feasible control paths**, mechanically checked against branch targets/fallthrough by `classify.py`. They are not measured frequencies, whole-loop averages, throughput estimates or instruction-count speedup predictions. Full disassembly and exact path address lists are retained.

### Text: placement improved, physical evaluation/branch structure remains

In the on image, inspect starts at0x100000d44. Length is now cached inX13 at0x100000e28 and rune inX9 at0x100000ec8. Off reloaded length at e30 and rune repeatedly at ed0/ee8/f00/f18. These are real improvements, not a refusal/no-op SSA build.

The call-free rune loop is now e30..f6c. At ec4 the rune is still written to FP-0x48. Sum evaluation ecc..ee8 still copies X26 through X0, pushes it16 bytes, copies W9 into W0, pops into X1, then does checked ADD/B.VS. The bool at FP-0x20 is loaded at f34 and stored at f2c/f64 on state changes; even assignments first read the old bool at f24/f5c. Separator control still materializes three CSET values, chains CBNZ/CBZ, then materializes !inside with another CSET. X25..28 still hold words/sum/cursor/snapshot; the new X9/X13 caches do not rename the original physical producers or eliminate expression stack.

There are8 helper calls on the normal nontrapping inspect invocation path outside the rune loop: d9c retain; dc8/e04 release; f84/fb0 release;1048/1074/10a0 release. Each has the existing4-home save/reload envelope. This is per invocation, **not per rune**. Some releases receive zero, but classifying their full ownership state is outside this audit. C has no calls within its nested text loops. This static audit does not attribute the measured gap to those calls versus loop work.

The current SSA implementation explains a concrete acceptance limit: inside=false is stored at d84 before3 helper calls and is first read after them. mir_ssa.build creates an unknown frame-memory version at every grouping call barrier; interference rejects an entire cell web if it demands an entry/post-barrier memory version (kind1/7). There is no preheader/fence reload or live-range splitting. Thus a value can remain in memory throughout a call-free loop because its initial definition preceded a call. This is a source/CFG deduction, not a captured per-function refusal diagnostic; additional allocation constraints could also apply.

C text is not a semantics identity: it terminates at NUL while Dunder iterates an explicit retained string length and supports embedded NUL; C validates UTF8 while decoding whereas Dunder's valid snapshot was validated at creation. Keep Dunder's length/lifetime and checked arithmetic. The selected C path is a comparison of code shape, not permission to copy its string contract.

### Sort: the shift is already register-resident; repeated values/addresses remain

The on array.sort entry is fc8. The shift101c..105c has exactly the same instruction sequence as off1024..1064 after relocation. j-1 is recomputed at1028,1044,1054; the source address is recomputed at102c/1048. The value loaded at1030 is compared with X7, then reloaded from the identical address at104c before its first intervening store at1050. There is no intervening call/store and X4(base)/X10(j) do not change. These are concrete pure-expression and normal-memory availability opportunities. A frame-only allocator cannot remove them.

C's corresponding550..568 loop retains the loaded predecessor inX2 and updates an address with postdecrement STR. Its7 instructions are LDUR/CMP/B.LE/STR/SUB/CMP/B.GT, with1 load+1 store. Dunder has3 SUB,3 address ADD,2 load,1 store,1 MOV,2 CMP,3 branches and2 NOP on the chosen17-instruction path. General value numbering/coalescing can address repeated pure arithmetic; carrying the array load needs an explicit ordinary-memory/provenance contract. Loop rotation/derived-pointer induction and target addressing selection are further opportunities, each with its own proof.

The surrounding on main is still largely legacy physical code. Fill3a4..498 reloads FP induction/seed/repeat/descriptor, uses expression stack, performs generic checked remainder (including materialized MIN/-1 guards) and calls actual managed push at488. C fill4e0..510 uses register induction, hoisted reciprocal constants and postincrement STR. The Dunder push call additionally maintains length/capacity and allocation traps; replacing it with an unchecked store requires a general builder/capacity/trap-order proof, not a benchmark shortcut.

Checksum4c0..580 reloads the array descriptor length/element shift/data every element (4f4/504/508, then element518), retains a bounds branch, and spills both checksum and induction through FP. C checksum57c..5a0 retains the scalar loop state and needs one element load; multiplication/addition overflow checks still remain in C. No instruction-only evidence says all Dunder checks can be removed: proving values.len==256 through the preceding push loop is beyond current MIR facts.

## Next coherent compiler step

Extend the existing SSA graph into an **allocatable value backend**, rather than another physical-frame read cache. Current mir_ssa intentionally pins all original physical GP/NZCV operations, assigns one GP home per complete cell phi-web, keeps frame stores write-through, refuses demanded unknown memory versions, and never represents expression-stack values as allocation candidates. mir_value_prop currently creates identity facts only for Constant/Copy/MOVK and kills arithmetic/load results. Those exact limits match the residual text and sort patterns.

First verifiable slice: split scalar live ranges at fixed-register/call/memory fences; insert explicit reload/sync points; give ordinary scalar producers and balanced private expression-stack values virtual identities; coalesce copies; remove dead stores only when no observer can see them; retain explicit NZCV/check/short-circuit dependencies. A bool can reload once after the setup calls, flow through loop block parameters, and synchronize before a possible memory observer, without inventing NoModRef for calls. A call-free balanced expression-stack region can evaluate the sum directly from virtual values, without conflating stack arguments or escaped SP addresses with private expression temporaries. Phi/edge moves, spills, physical constraints and rollback/budgets must remain explicit and verified. Predicate-only values should lower to control edges without unnecessary CSET materialization. This targets text and the still-spilled checksum loop.

In that same value representation, add bounded pure arithmetic value numbering; this can recognize sort's repeated j-1 and source address without a heap alias assertion. To also reuse the first array load, introduce explicit managed object/address provenance plus ordinary/nonvolatile memory versions, widths/extensions and lifetime. Calls, possibly aliasing stores, escaped/unknown/volatile memory must invalidate availability; first-successful-load dominance must preserve traps. Start with local dominated load reuse with no intervening write/call. Current source_objects-v1 only separates indirect objects from unexposed private frame cells; it is **not** that heap-load contract. Loop-invariant descriptor placement and derived-pointer induction should consume these same facts, preserving zero-trip and checked ordering.

This is not a promise that either stage meets the C gate. Whole-function source-independent before/after dumps are needed to distinguish memory-fence refusal from coloring/profitability, and to prove which new stage changed which operations. Minimum dump additions: stable op/value/block IDs and edge arguments; call semantic-input versus clobber/NZCV masks; frame-cell views and unknown-memory fences; allocation intervals/constraints and reload/spill/parallel-copy reasons; memory provenance/version/invalidation; rewrite/refusal reasons; final op-to-native-address map and image/ABI/policy hashes. Keep sparse bounded per-function arenas and atomic refusal; avoiding a new quadratic compiler cost is part of this architectural step.
